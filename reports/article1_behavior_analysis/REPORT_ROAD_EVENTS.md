## Events come from the map

An event here is a **place on the map the vehicle reached**, never a pattern
spotted in the signal being analysed. Defining a braking event from the speed
trace and then reporting a speed response to it would be circular; defining a
roundabout from OpenStreetMap and then asking what speed did is not.

## Windows

All in seconds, anchored to the event's start for the negative offsets and to its
end for the positive ones — so a 40 s roundabout and a 2 s junction both get "the
ten seconds after it finished".

| window | offsets |
|---|---|
| pre-event | −10 → −3 s |
| approach | −3 → 0 s |
| post-event | 0 → +10 s |
| physiological baseline | −30 → −10 s |
| anticipation | −10 → 0 s |
| immediate response | 0 → +10 s |
| delayed response | +10 → +40 s |

Windows are clipped to the recording and trimmed away from neighbouring
manoeuvres; every clip is recorded on the row with its reason. Each signal family
— vehicle at 1 Hz, head at frame rate, PPG at beat times, light at 9 Hz, gaze
where a block covers it — is windowed on **its own real samples**.

## Two structural fixes the first run forced

The first run produced no usable baseline for roundabouts or curves at all. Both
causes were real and are now fixed:

1. **Every node of an OSM roundabout is shared between the ring and an approach**,
   so the topological junction rule turned each roundabout into a dense cluster of
   generic junctions that blanketed it and left nowhere clean to take a baseline.
   Roundabout nodes are now excluded from the junction feature set.
2. **`curve`, `straight` and `road_class_change` partition the whole drive between
   them** — every metre is in one of them — so treating them as contaminants left
   nothing anywhere with a clean baseline. Worse, the straight before a curve is
   exactly the baseline that curve wants. Only salient kinds (roundabouts,
   junctions, signals, crossings, stops) can now spoil a neighbour's window, and
   sub-events of one manoeuvre never trim each other.

## Event-related heart-rate change

Median change from the local −30 → −10 s baseline to the 0 → +10 s window:

| event | car Δ | n | motorcycle Δ | n |
|---|---:|---:|---:|---:|
| roundabout traverse | **+13.2 bpm** | 2 | **+7.6 bpm** | 6 |
| pedestrian crossing | +14.3 bpm | 3 | −15.0 bpm | 4 |
| junction crossing | +8.1 bpm | 4 | +0.3 bpm | 46 |
| curve | +30.0 bpm | 1 | +9.2 bpm | 5 |
| straight | **−4.0 bpm** | 2 | **−5.3 bpm** | 8 |

The direction is consistent and is the one a reader would expect: heart rate
rises around roundabouts and curves and falls on straights, in both vehicles.

**The counts behind those medians are single digits for almost every row.** A
median of two values is not an estimate of anything. The only row with a
respectable n is the motorcycle's 46 junction crossings, and it shows
essentially no change (+0.3 bpm) — which is itself worth noting, since junctions
on that route were mostly minor side roads crossed at speed.

Many events produce no delta at all because their baseline window was clipped or
trimmed to nothing; that is recorded per row rather than silently dropped.

## Head motion around events

Median |head yaw rate| in the immediate window:

| event | car | motorcycle |
|---|---:|---:|
| roundabout traverse | 0.123 rad/s | 0.110 rad/s |
| junction crossing | 0.059 rad/s | 0.063 rad/s |
| curve | 0.150 rad/s | 0.107 rad/s |
| straight | 0.147 rad/s | 0.246 rad/s |

These do not separate cleanly, and the straight-road values being the *highest*
suggests the yaw-rate measure is picking up scanning behaviour rather than
manoeuvre-driven head turns. It should not be over-read.

## Language

Physiological changes around events are described as **autonomic response
candidates** / **event-associated heart-rate change**. An increase is never
called stress, arousal or workload. With one participant and one session there is
no basis for any of those labels.
